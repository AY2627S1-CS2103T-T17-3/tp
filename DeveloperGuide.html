Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

Model component

API : Model.java

The Model component,

  • stores the address book data i.e., all Person objects (which are contained in a UniquePersonList object).
  • exposes one filtered ObservableList<Person> for the current search and status view. The UI observes this list, so it updates when either filter changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Tag normalizes valid alphanumeric names to lowercase with Locale.ROOT. Its equals and hashCode use that normalized name, so Person's Set<Tag> collapses Publicity and publicity into one tag. Command parsing, CSV import, and JSON loading all construct Tag objects and share this rule. Saving writes the lowercase names.

Person represents name, phone and address as non-null Optional containers. Email, status and tags remain required. The complete-record constructors retain their non-null argument requirements and delegate to the constructor accepting optional contact details and an explicit status. The corresponding getters return Optional<Name>, Optional<Phone> and Optional<Address>. The value classes retain their strict validation: absence is a property of the member, not an empty Name, Phone or Address.

Email validates a complete address with the exact domain u.nus.edu and stores it in lowercase using Locale.ROOT. It does not trim whitespace; model values and saved strings containing surrounding whitespace are invalid. Command parsing trims surrounding argument whitespace using the trim() behavior. The existing local-part expression is unchanged: letters and digits may be separated by single +, _, ., or - characters, but punctuation cannot lead, trail, or appear consecutively. Validation uses the normalized whole string; no new Unicode support is introduced. The normalized local-part has an inclusive maximum of 64 UTF-16 units. Different local-part aliases remain distinct. The suffix is literal: @nus.edu, @sub.u.nus.edu, @u.nus.edu.com, and @uXnusXedu are invalid. Construction, command parsing, CSV import, and JSON loading share the email-validation rule. Email-substring searches retain their existing independent rules, including substrings longer than 64 characters.

Person.isSamePerson compares canonical emails only. Members can share a name or phone number when their emails differ. UniquePersonList uses this identity rule for addition, replacement, and bulk replacement, while Person.equals still compares every field. Add and edit detect email conflicts across the complete directory, including members outside the displayed filter, and identify the existing member by email and, when present, name without a displayed index. Re-entering one's own email or changing only its case remains valid; changing an email releases the previous one for reuse.

EditCommand preserves tags; EditPersonDescriptor accepts only name, phone, email, and address. EditCommandParser still tokenizes t/ so it can reject tag arguments explicitly instead of including them in another field's value.

TagAddCommand and TagRemoveCommand each accept one displayed index and one tag. Their parsers reuse ParserUtil.parseIndex, ParserUtil.parseTag, and duplicate-prefix validation to enforce this scope. Each command resolves the person from Model.getFilteredPersonList(), copies their immutable tag set, and adds or removes the requested Tag using the existing case-insensitive identity rule. It then constructs a replacement Person with unchanged contact details and calls Model.setPerson.

Adding an existing tag succeeds with the normal completion message and leaves the record unchanged, while attempting to remove an absent tag throws a CommandException and leaves the record unchanged. Removing the final tag is allowed. After success, both commands clear the search and show members in the selected status view, matching EditCommand. LogicManager saves the updated address book through the existing storage flow; no storage schema or UI changes are required.

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in AddressBook, and each Person references tags from that list. This lets AddressBook maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

MainApp configures data/nusocietydesk.json and preferences.json beside the packaged JAR. It passes these paths to storage, and the member data path to the UI. When running from compiled classes during development, or when the code source location is unavailable, both paths are relative to the working directory.

The JSON root, property names and email string are unchanged. JsonAdaptedPerson writes absent name, phone and address fields as explicit null values. Missing properties and explicit nulls load as empty optionals; supplied strings still use the existing validators without trimming. Empty or whitespace-only strings are invalid. Valid complete records still load. JsonAdaptedPerson writes a lowercase status; active and archived load unchanged, while a missing or null status defaults to active. No migration or schema-version field is introduced. JsonAddressBookStorage.loadAddressBook returns an AddressBookLoadResult with a status (SUCCESS, PARTIAL, FAILURE, or MISSING), recovered records, and errors. Each record is deserialized and validated independently. Invalid records and later duplicate canonical emails are skipped. Error positions refer to the original one-based positions in the saved persons array, including skipped records; a duplicate reports both positions, for example Record 3: email "alex@u.nus.edu" duplicates record 2. Malformed JSON, trailing content, invalid roots, missing or non-array persons values, and read failures produce a failed load with no recovered records. The existing readAddressBook API remains strict and throws DataLoadingException on any loading error.

MainApp.initModelManager uses recovered records and prepares a warning for UiManager to display after the main window opens. Any partial or failed load disables saving through that storage instance for the rest of the session, including direct calls to either save overload. LogicManager rejects commands that change records before execution, while list, view, find, findall, findany, help, and exit run without saving. New commands require write access by default and must explicitly override Command.isReadOnly to run during recovery. Repairing the file requires a restart to restore saving. Only a missing file starts with sample members; a valid empty file stays empty. Valid mixed-case emails become lowercase in memory on load and in the JSON file after a normal successful save.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Viewing the offline command reference

AddressBookParser delegates help arguments to HelpCommandParser, which implements Parser<HelpCommand>. The help parser creates a command only when its trimmed arguments are empty; surrounding whitespace is allowed. Extra arguments, such as help 1, produce the existing invalid-command-format error with HelpCommand.MESSAGE_USAGE before any command executes or the Help window opens. Other commands retain their argument handling. HelpCommand provides a single bundled MESSAGE_HELP string containing a description, usage, and example for each of the 16 implemented commands, including all five find forms and a notation legend. Examples are text only and are never executed. The command does not read or change the model. It remains read-only for startup recovery and overrides requiresSave() to return false, so LogicManager also skips saving in normal sessions, including when saving would fail. No model, storage-schema, or preference changes are needed.

The command returns SHOWING_HELP_MESSAGE (Opened help window.) with showHelp true and exit false. MainWindow displays this short acknowledgement through ResultDisplay and opens or focuses the existing HelpWindow. The window sets its read-only, wrapping commandReference text area to HelpCommand.MESSAGE_HELP. Its vertical layout keeps the existing User Guide message and Copy URL button above the scrollable reference. The Help window is resizable, with a default content size of 760 by 560 pixels and minimum window dimensions of 450 by 300 pixels. Submissions retain existing command-history behavior.

F1 and Help → Help open the same window with both the guide link and the reference. The User Guide message and Copy URL action are unchanged, and the URL is not repeated in the reference. There is no browser integration, bundled full guide, new dependency, or persisted help state. The known minimized-help-window behavior remains unchanged.

HelpCommandTest checks the exact reference and parses its examples without executing them. HelpCommandParserTest covers empty and whitespace arguments, rejected arguments, and null input. AddressBookParserTest checks dispatch and existing error handling. LogicManagerTest checks unchanged records, search and status, missing and existing files, a failing save implementation, and startup recovery. MainWindowTest checks the short acknowledgement, reference placement below the guide link, wrapping, popup reuse, and F1/menu access with an unsent draft. It also checks that rejected help arguments retain editable input with error styling and do not open a popup.

Confirming a directory clear

AddressBookParser delegates clear arguments to ClearCommandParser. Only empty trimmed arguments are accepted. Extra arguments produce MESSAGE_INVALID_COMMAND_FORMAT with ClearCommand.MESSAGE_USAGE before confirmation or execution.

MainWindow calls Logic.execute(commandText, clearConfirmation) with a callback that opens a JavaFX confirmation dialog. After parsing and checking startup recovery protection, LogicManager invokes this callback only for ClearCommand, before taking a snapshot, executing the command, or saving. The single-argument execute method supplies no approval and therefore cancels a valid clear. The logic layer has no JavaFX dialog dependency.

The dialog describes deletion of all members, including archived, hidden, existing, and imported members, and suggests delete INDEX for one member. Cancel is the default and initially focused button. Escape, closing the dialog, and Cancel return false, producing Clear cancelled. without changing records, search, status view, or the saved file. Cancellation is a completed submission: the command box clears and the submission remains in history. Only Delete all members returns true. ClearCommand then empties the entire directory through the existing save-and-rollback flow. The status view is retained. Even an empty directory requires confirmation.

ClearCommandParserTest and AddressBookParserTest cover strict syntax and surrounding whitespace. ClearCommandIntegrationTest checks confirmation timing, cancellation without saving, persisted deletion of hidden and archived members, save-failure restoration, and startup recovery protection. MainWindowTest exercises the actual dialog, safe defaults, keyboard cancellation, window closure, and confirmed clearing.

Recalling submitted commands

UI ownership and history state

CommandBox owns one JavaFX-independent CommandHistory. A key-pressed filter on its text field consumes plain Up/Down events, including boundary no-ops, before JavaFX moves the caret. Modified arrows and other keys are not intercepted. The existing CommandExecutor remains the only path to execution; navigation never invokes it, updates the result display, or accesses Logic, Model or Storage.

The partial class diagram shows the owned history helper, the saved input snapshot, and the separate execution callback. CommandExecutor is supplied by MainWindow as this::executeCommand; it is only called on submission. InputState is a nested immutable record used for navigation inputs and results as well as the saved draft. The diagram omits JavaFX controls, inherited UI members, and private helper methods.

The helper uses two Deque<String> collections backed by ArrayDeque: commandsBeforeCursor holds older entries and commandsAfterCursor holds the selected entry followed by newer entries. Both are ordered oldest first; their concatenation is the complete retained history. An empty commandsAfterCursor denotes the draft position. Up moves the last older entry to the front of commandsAfterCursor; Down moves its first entry back to the end of commandsBeforeCursor. Each arrow transition uses constant-time deque end operations.

Recalling an entry and restoring a draft

The first actual Up transition captures an immutable InputState containing exact draft text, selection anchor and caret. Down past the newest entry returns that snapshot and clears it. Recalled entries place the caret at the end. Before moving in either direction, the helper saves the selected entry's edited text in editedCommands, keyed by its chronological index (commandsBeforeCursor.size()). These indices remain stable until submission. Using indices keeps separate occurrences of the same command independently editable. The map contains at most one temporary string per retained entry, including empty edits. Reverting an entry to its submitted text removes its temporary edit. Returning to the draft does not clear edits, so browsing again restores them. Stored submitted strings and duplicate detection remain unchanged. A returned empty optional denotes a no-op; a present result always restores text/selection and explicitly removes error styling, even when the replacement text is identical. Boundary no-ops preserve edits, selection and styling.

For example, after submitting list and help, the user types an unsent draft and presses Up to recall help. Now commandsBeforeCursor contains ["list"] and commandsAfterCursor contains ["help"], so the selected entry's index is 1. If the user edits the recalled text and presses Down, the helper stores the temporary edit under that index and restores the draft's exact text and selection. The next Up restores the edit with the caret at the end, while the submitted string remains help. None of these navigation steps executes a command.

Recording submissions and handling failures

record ignores String.isBlank() input without changing any state. CommandBox separately checks String.isBlank() to decide whether to execute the submission. For every other submission it resets the cursor, clears all temporary edits and the saved draft, suppresses an exact consecutive duplicate, and otherwise appends the raw string. MAX_HISTORY_SIZE is 100 across both deques. At capacity, the oldest entry is removed before appending. Blank inputs and suppressed duplicates do not evict entries; the draft is separate. Resetting the cursor moves at most 100 entries. No evicted entry is retained elsewhere. Recording precedes the executor call, so parser, execution, import and save failures are recallable. Duplicates still execute. Success clears the field; failure retains the input and existing error styling. After a parser or command exception, CommandBox calls selectLatestAfterFailure to select the newest entry without replacing the field or its selection. The first Up therefore reaches the preceding entry, while Down can return to the failure. If no preceding entry exists, Up is a boundary no-op preserving error styling. This positioning leaves draft null, so there is no duplicate failed-input draft beyond the newest entry. Down is a boundary no-op when only the newest entry remains in commandsAfterCursor and there is no saved draft. Repeated Down presses preserve edits and selection; the next Up still recalls the preceding entry. Normal browsing captures and restores a real unsent draft as before. Temporary edits survive navigation.

For example, after list succeeds and lisst fails, the cursor selects lisst with no saved draft. Up recalls list; Down returns to lisst; another Down is a no-op. This avoids showing the failed input twice. An exact consecutive duplicate still reaches the executor, but neither adds an entry nor evicts one.

History is local to the command box's lifetime. Focus changes, Help, minimizing and ordinary commands do not reset it; a new application instance starts empty. It is never serialized or reconstructed from logs. The existing command syntax, direct parser behavior, data schemas, recovery/save behavior and execution logs are unchanged. Recalled indices are interpreted against the current displayed list when submitted.

History diagnostics and assertions

CommandHistory obtains its logger through LogsCenter. It emits FINE messages for recording, duplicate suppression, ignored blanks, failure selection, navigation, draft restoration and boundary no-ops. Messages contain counts, direction and an eviction flag only, never command or draft contents. Examples include Command history recorded: size=100, evictedOldest=true. and Command history navigated older: before=99, after=1. Restoration logs only Command history draft restored: size=100. rather than an additional newer-navigation event. These normal operations are not warnings. Lazy message suppliers avoid building diagnostic strings when FINE is disabled. Existing logging destinations and default levels are unchanged; enabling FINE in the existing logging configuration exposes the diagnostics.

Java assertions check stable operation boundaries, including no-op returns: non-null deques, combined capacity, nonblank entries, no adjacent exact duplicates across the complete history, and any saved draft requiring an active browsing position. Browsing after failure has no saved draft. Draft assertions validate text and selection bounds; pending-edit assertions check that at most one non-null edit exists per retained index. Operation assertions check removal prerequisites, unchanged navigation size, the expected recording size, and cursor/draft reset after submission. Messages identify invariant failures without including input text. Assertion expressions and invariant helpers have no side effects; required mutations and all user-input decisions use ordinary control flow. AssertionError is not converted to command feedback. A separate test task verifies behavior with assertions disabled.

JUnit tests cover recording, capacity/eviction (including submission while browsing), draft selection, retained edits in both directions and across draft visits, independent edits to repeated commands, empty edits, and clearing edits after submission without changing original submitted history, duplicate and whitespace rules, failure recall, key modifiers and event consumption, identical-text styling, and metadata-only logs. GUI tests share one JavaFX toolkit per worker and require a display. See the testing guide for the assertions-disabled check and the manual history scenarios below.

Archiving and activating members

archive INDEX and activate INDEX use the index in Model.getFilteredPersonList, so they work after a search. Each command rejects an invalid index or a member already in the requested status. Person.withStatus creates a replacement that retains the member's optional contact details, email and tags. Model.setPerson replaces the record in the directory; its email identity remains unchanged. A successful command clears the search while retaining the selected status view. Archived members appear in All or Archived view and can be selected for activate there. Changing a member's status can remove them from the current view. LogicManager saves the new status through the existing JSON storage after each successful command.

Filtering the member list by status

The button in MainWindow.fxml starts at ALL. MainWindow.handleStatusFilterButton cycles the state ALL → ACTIVE → ARCHIVED → ALL through Logic.setStatusFilter. The view all|active|archived command sets the same state directly. LogicManager passes both paths to ModelManager, the source of truth for the selected view. MainWindow reads the state to update the button text and colour after either path changes it. After a button click, MainWindow replaces the previous result feedback using ViewCommand.MESSAGE_SUCCESS, matching the typed command's confirmation. This is an in-memory setting and starts at All on each launch.

ViewCommandParser accepts exactly one status, ignoring case. ViewCommand is read-only so it works during data recovery; it also skips the normal save because selecting a view does not change member records.

The sequence diagram shows a typed view archived followed by one button click. Both paths change the same model filter and update the list; the typed command also synchronizes the button after execution. The command path shown is a normal writable session. In recovery mode, LogicManager permits this read-only command and executes it without saving as well.

ModelManager keeps one FilteredList<Person> and two independent filter settings: the current search predicate and the selected StatusFilter. Each change recomputes the list predicate as search and status. Changing views therefore keeps a search; a new find, findall, or findany searches the complete directory and replaces the previous search while the status view stays selected. list clears the search predicate but keeps the status view. Commands that clear a search after a successful data change do the same. Find feedback counts only members visible in the selected view. edit, tag, untag, archive, activate, and delete resolve their index against this same FilteredList<Person> at execution time. They reject an index beyond the visible list, even when that index exists in the full directory. Edits, tag changes, archives, and activations then clear the search but retain the status view; deletion leaves the current search in place.

Recording a member with incomplete contact details

add e/EMAIL [n/NAME] [p/PHONE_NUMBER] [a/ADDRESS] [t/TAG]... requires only email. All eight combinations of the other contact fields are accepted. AddCommandParser checks for the email prefix and a valid preamble, rejects repeated contact prefixes, then validates supplied name, supplied phone, email, supplied address and tags in that order. Omitted optional prefixes become empty optionals; supplied blank values still fail validation. Existing tokenization is unchanged: recognized prefixes need an ordinary preceding space, and unknown prefix-like text may become part of a field value. New members have active status and may have tags.

EditCommand uses the descriptor's supplied values or the member's existing optionals to construct the replacement. An omitted edit preserves either the value or its absence. Blank edits cannot clear a detail. Tags and status are preserved. Tag commands also pass the optional contact details and status through unchanged. Add and edit still check email conflicts throughout the directory; a repeated add never merges records. Successful add, edit and tag commands clear the search and show members in the selected status view.

Add, edit, tag and delete commands use Messages.formatProvidedDetails to omit absent contact fields and empty tags from their success messages. The formatter label a supplied name as Name: <person name> consistently across command confirmations. Unnamed duplicate errors identify the existing member by email only. PersonCard uses the canonical email as its heading when the name is absent. Its separate email label is then both invisible and unmanaged, so it contributes no layout space. When a name is present, the heading uses that name and the email row is visible and managed. Headings never wrap: both names and emails used as headings stay on one line, with an ellipsis when they exceed the available width. Phone and email rows also remain on one line. Full values are available in tooltips and are not shortened in the model or saved data. Phone, address and email rows always include Phone: , Address: and Email: respectively; missing phone and address values use - after their labels. Full-text tooltips include these prefixes. The content VBox in PersonListCard.fxml uses TOP_LEFT alignment, five pixels of top padding and a shared 105-pixel minimum height. Short, single-line headings and shared fields keep the same offsets from the top of each card when the last email row is hidden. Unused space stays below the content. Cards with short details share the same height; wrapped address text and additional rows of tag badges can make cards taller, so their height is not fixed. All other card fields remain on one line. The heading row uses TOP_LEFT so the index stays aligned with the heading. Fields below a wrapped address or additional tag rows move down naturally.

These display rules apply to active and archived members regardless of whether they were added, imported or loaded from JSON. PersonListPanel constructs a new card when a member is replaced, so supplying a name through edit restores the email row through the existing list refresh. No new model state or storage field is needed. Name and phone predicates return false for absent fields. Email search remains available, and display placeholders are never model values. A supplied address of - remains valid and looks the same as a missing address; this display change does not alter validation.

JsonAdaptedPerson maps between optional model values and nullable saved strings. An email-only record can be represented as {"name":null,"phone":null,"email":"alex@u.nus.edu","address":null,"status":"active","tags":[]}. Reading does not rewrite the file; the next successfully saved command writes explicit nulls. Older versions requiring complete contact details reject the entire file if it contains an incomplete member. With their existing loading behavior, they may then overwrite that file after a successful command; users must back up before downgrading.

Automatic saving uses save-failure recovery. CSV import also accepts absent name, phone, and address, but requires status.

Tests cover optional-field combinations, unchanged validation, explicit null persistence, legacy loading, incremental completion across reloads, filtered edits, unnamed duplicates, email reuse, searches, tags and deletion. The import regression checks supplied-field validation and that imported emails conflict with existing incomplete members. PersonBuilder supports absent fields and preserves status when copying a member; PersonUtil omits absent prefixes when generating commands. PersonCardTest checks all eight optional-contact combinations, exact labels and tooltips, conditional email visibility and layout participation, and narrow named and unnamed cards containing maximum-length emails. Rejecting Unicode blank addresses

Address.isBlankAddress recognizes empty strings and strings consisting only of Unicode White_Space characters, including U+3000, U+2003, and nonbreaking spaces. It uses a separate \p{IsWhite_Space}* pattern. Address.isValidAddress retains its original [^\s].* condition and additionally rejects these blanks; the original expression's flags, leading-character restrictions, and line-terminator behavior are unchanged. The shared error is Addresses must contain at least one non-whitespace character and be at most 200 characters long. U+200B ZERO WIDTH SPACE and U+FEFF BOM are outside this blank classification.

Add/edit reuse this model validation through ParserUtil.parseAddress, after the existing trim() calls. Invalid supplied addresses fail before execution or saving, preserving records, search, status view, and JSON. Omitted addresses retain their optional-field semantics. Nonblank address strings receive no new normalization. The top-level add/edit parser can reject U+0085, U+2028, and U+2029 as command-format errors before address validation; tokenization and error precedence remain unchanged.

CsvMemberReader uses Address.isBlankAddress after its existing field trimming to map Unicode blank cells to absent addresses. Commons CSV still ignores surrounding Java whitespace in unquoted fields before the reader calls trim(); quoted Unicode spaces inside a cell can therefore reach the model unchanged. Tests include both quoted and unquoted blanks. Other fields retain their current rules.

JSON strings use the shared validator without trimming. Legacy Unicode blank addresses follow the existing protected recovery path: the affected member is skipped, valid members load, errors retain original record positions, and saving is disabled until repair and restart. Strict readAddressBook still throws DataLoadingException on any error. Missing or null addresses remain absent; no schema or migration is added.

AddressTest covers all 25 whitespace code points, mixtures, classification boundaries, and existing restrictions. Add/edit parser and logic tests cover rejection, exact feedback, and state/file preservation. CSV reader and import integration tests cover absent-address persistence; AddressBookRecoveryTest covers protected JSON loading.

Bounding contact and tag lengths

Name, Phone, Address, and Tag each define a MAX_LENGTH constant and enforce it in their existing isValid... method before matching a regular expression. Constructors reuse these validators. The existing character restrictions, optional contact fields, address blank classification, and lowercase tag identity remain unchanged. Phone.VALIDATION_REGEX also expresses its 3-to-15-digit range.

Field Inclusive length range Basis for the maximum
Name 1 to 127 NUS's documented full-name requirement is fewer than 128 characters.
Phone 3 to 15 digits The international E.164 numbering limit is 15 digits; the existing minimum of 3 is an application rule.
Address 1 to 200, with nonblank text The published Myinfo Singapore address components fit into 174 characters in the representation below, leaving 26 for additional formatting or accommodation details.
Each tag 1 to 30 An application policy for concise member categories; internationalstudentambassadors fits at exactly 30 characters.

The name maximum follows the NUS Canvas name data standard, which says a full name must be less than 128 characters. We adopt its length bound; this change does not expand the existing name character rules. This is a local product choice, not a universal maximum for human names.

The phone upper bound follows ITU-T Recommendation E.164. The app continues accepting digits only and does not validate country-code allocation, number ownership, or whether a number is in service. Its 3-digit minimum also allows short numbers already accepted by the app. Using the E.164 upper bound does not make this a complete E.164 validator.

We size addresses for NUS students' current Singapore residences, including campus rooms and rented apartments. The published Myinfo v4 AddressSG schema allows block/house number 10, street name 66, building name 65, floor 3, unit 5, and postal code 6 characters. Together with the 9 letters in Singapore, these components total 164 characters. In the representation [block] [street], #[floor]-[unit], [building], Singapore [postal], spaces and punctuation add 10, giving 174. The 200-character cap adds 26 characters of headroom. This is a calculated bound for that schema and formatting, not a claim that Singapore has an officially longest address or a nationwide 200-character maximum. The address remains free text; geographical or postal-code existence checks are not introduced.

Validating email length safely

The local-part regular expression contains a repeated group. Matching a sufficiently long, punctuation-separated candidate can consume excessive stack space and cause StackOverflowError. Email.getValidationError checks the normalized local-part length before pattern matching, bounding the recursive group matching.

The helper counts UTF-16 units before the first @, or across the whole candidate if @ is absent. It returns Email local-part must contain at most 64 characters; received N. when that count exceeds 64, Email.MESSAGE_CONSTRAINTS for other invalid values, or an empty optional for a valid email. Email.isValidEmail and the constructor reuse this helper, keeping the validation rule in the model.

Callers adapt the selected error to their existing failure handling. ParserUtil.parseEmail throws ParseException before command execution or saving; the UI displays the message and retains editable input with error styling and history. CSV import adds the original record number and rejects that record while processing other records. JSON loading adds the saved record position and uses the protected recovery path. Each caller retains its existing field-validation order.

Importing member directories from CSV

Import adds valid, nonduplicate members while reporting rejected records in CSV order. It separates file parsing from changes to the live model so a fatal file error cannot leave a partially imported directory. See the User Guide for the CSV format and user-facing examples.

The main responsibilities are:

  • AddressBookParser dispatches to ImportCommandParser, which parses one local path without file I/O.
  • CsvMemberReader parses the complete UTF-8 file with Apache Commons CSV before validating member records. It returns an immutable list of CsvMemberRecord outcomes: each contains the original record number and either a valid Person or its first validation error.
  • ImportCommand checks those outcomes against a temporary AddressBook and applies the accepted members together.

The execution flow is:

  1. Protect the source. Before execution, LogicManager derives the application home from its code location: the real JAR's parent folder for packaged runs, or the working directory for IDE/Gradle runs. It resolves the source with Path.toRealPath and checks containment using Path.startsWith, so parent traversal, symbolic links to outside files or folders, and similarly named sibling folders cannot escape the boundary. Both absolute and working-directory-relative paths are accepted when their real location is inside the home folder. It also compares the CSV path with the JSON save path using normalized paths and Files.isSameFile, rejecting aliases and links to the save file. These checks complete before CSV parsing, model changes, or saving. The reader opens the source for reading only.
  2. Read and validate. The reader checks the fixed six-column header, trims member fields, and reuses the model validators. Blank name, phone, and address values become empty optionals. Email and status are required; Status.isValidStatus accepts only active and archived. Tag and Set<Tag> normalize and deduplicate tags.
  3. Stage accepted records. The command copies the complete directory, including archived and filtered-out members. It collects validation errors and checks valid records against the copy's email identity rule, adding each accepted member to that copy. This also detects duplicates of earlier accepted CSV records; invalid records reserve no email.

It compares the accepted members with the resulting visible list and adds their hidden count and a view all hint when needed. Existing members and rejected records do not contribute to that count. Saving member data safely

Saving protects both the in-memory directory and the existing JSON file. Commands that change member records return success to the UI only after persistence succeeds. Read-only commands (find, findall, findany, list, view, help, and exit) return false from requiresSave() and execute without attempting to save. They remain available when a previously loaded data file becomes unwritable. In a normal writable session, parsing and pre-execution guards run first, including confirmation for clear. For commands that require saving, LogicManager then follows this sequence:

  1. Snapshot. Copy the directory and capture Model.getFilteredPersonListPredicate() before executing the command.
  2. Execute. Run command.execute(model). A parser or command exception exits before saving; the save-failure rollback below does not handle command-execution failures.
  3. Write. Delegate saving through StorageManager to JsonAddressBookStorage, which serializes the complete directory before invoking its package-private AtomicFileWriter helper.
  4. Replace. The writer creates a temporary file beside the destination, writes and closes its UTF-8 contents, then replaces the destination with Files.move(ATOMIC_MOVE, REPLACE_EXISTING). Existing symbolic links are resolved to their target so the configured link remains intact. There is no non-atomic fallback.
  5. Return or restore. After replacement succeeds, return the command result. On IOException (including AccessDeniedException) or SecurityException from saving, restore the directory and previous search predicate, then throw a CommandException explaining the failure. The selected status view stays unchanged. The success result is not returned.

Restoring the search predicate, rather than just the visible list, preserves subsequent search behavior, including searches that matched no members. For example, if an import updates the model but atomic replacement fails, its accepted members disappear and the previous search is restored; the existing JSON and CSV source remain unchanged.

After a failed write or replacement, the writer attempts to remove the temporary file. A cleanup failure is attached to the original exception and logged. No fallible cleanup follows a successful replacement, and a failed first save leaves the destination absent. Logs identify the command class and recovery metadata without raw input or member details.

This covers ordinary write and replacement failures, not power loss or concurrent edits by another application. User-preference saving is unchanged. The separate startup recovery guard rejects member changes and disables saving after a partial or failed load; it is not the rollback mechanism described here.

[Proposed] Undo/redo feature

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedAddressBook. It extends AddressBook with an undo/redo history, stored internally as an addressBookStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedAddressBook#commit() -- Saves the current address book state in its history.
  • VersionedAddressBook#undo() -- Restores the previous address book state from its history.
  • VersionedAddressBook#redo() -- Restores a previously undone address book state from its history.

These operations are exposed in the Model interface as Model#commitAddressBook(), Model#undoAddressBook() and Model#redoAddressBook() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedAddressBook will be initialized with the initial address book state, and the currentStatePointer pointing to that single address book state.

Step 2. The user executes delete 5 command to delete the 5th person in the address book. The delete command calls Model#commitAddressBook(), causing the modified state of the address book after the delete 5 command executes to be saved in the addressBookStateList, and the currentStatePointer is shifted to the newly inserted address book state.

Step 3. The user executes add n/David …​ to add a new person. The add command also calls Model#commitAddressBook(), causing another modified address book state to be saved into the addressBookStateList.

Note: If a command fails its execution, it will not call Model#commitAddressBook(), so the address book state will not be saved into the addressBookStateList.

Step 4. The user now decides that adding the person was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoAddressBook(), which will shift the currentStatePointer once to the left, pointing it to the previous address book state, and restores the address book to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial AddressBook state, then there are no previous AddressBook states to restore. The undo command uses Model#canUndoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.
